## Headline

**Delivery held perfectly — but latency roughly doubled, and `Get Booker` is now the
bottleneck.** Nothing failed, nothing was lost, every guard ran. The instance is as
robust as on 7 Sept, but noticeably slower under the same load, and the degradation is
concentrated in one node.

## How it was run

Ten identical read-only questions — "what studios are free next Thursday from 2pm to
5pm" — sent **overlapping**, all ten hitting Slack between **16:10:53.2 and
16:11:06.4 PHT** (08:10:53–08:11:06 UTC), a **13.7-second window**. Turns ran 12–28 s,
so every one of the ten was in flight when the last arrived — real contention.
Read-only on purpose: no calendar writes.

## The story is `Get Booker`

It degrades **monotonically by arrival order** — the earliest, most-contended turn waits
longest, unwinding cleanly as the queue drains. That is a serialization signature, not
noise:

† 5850 also had a lone `All Session Types` spike to **12,289 ms** (normally ~1.1 s) — a
second contention artifact on the same turn.

Two things worth flagging beyond the burst itself:

- **`Get Booker` regressed even serially.** On single turns earlier today it was already
  ~4.1–4.2 s (execs 5608, 5657, 5722, 5766), against ~1.1 s serial on 7 Sept. So the
  baseline moved *before* any concurrency — the burst then multiplied it to 12.5 s.
- **The likeliest mechanism is upstream serialization** on the Airtable booker lookup —
  e.g. Airtable's ~5 req/s per-base rate limit queueing the ten concurrent reads, or
  SQLite write contention (n8n is **still on SQLite** — the Postgres migration is listed
  but not done). Either way it did not fail; it queued.

**Net for capacity:** the hardening applied so far did not improve concurrency latency,
and `Get Booker` is now the node to watch. This is the top capacity item, separate from
the answer-quality work.

Recorded so the run is complete; no action from Genzo.

**The A1 non-determinism is unchanged, and the correct answer moved.** The
`Room Availability` sub-workflow **computed 20 rooms** on every turn this time — Likha,
Lobby, M3, M5, M7 + the 15 Studios. **M1 is no longer in the free set** (it was on
7 Sept). That is a real data change on the target date (16 Sept 2027), not a model drop —
worth confirming whether M1 was **booked** or **deactivated** since yesterday.

Against that computed truth of 20, the ten replies were:

| Variant | Rooms | Times | Correct? |
|---|---|---|---|
| Likha, Lobby, M3, M5, M7 + 15 Studios | 20 | 7 | ✅ correct & complete |
| 15 Studios only | 15 | 3 | ❌ drops the six non-Studio rooms |

Same failure mode and roughly the same ~30% rate as 7 Sept: the model reads "what
**studios**" literally and filters to `Studio`-prefixed names. The computation is not at
fault — it produced the correct 20 every time. This is the presentation layer, and it
remains the top build item (fix: enforce the list in the sub-workflow via `Guard Probe`).
