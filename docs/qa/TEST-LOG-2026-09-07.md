# Addendum — concurrency burst, 17:38 PHT

Requested by Genzo. Ten messages fired in a tight window to see whether the instance
degrades under simultaneous load.

## How it was run

Ten identical read-only questions ("what studios are free next Thursday from 2pm to
5pm"), sent **overlapping**, not one after another — all ten hit Slack between
**17:38:08.2 and 17:38:21.6**, a 13.4-second window. Because each turn takes about
9 seconds, the early turns were still running when the last arrived, which is what
creates real contention. Read-only on purpose: no calendar writes.

## Result: no degradation

| Measure | Serial run (17:16–17:23) | Burst (17:38) |
|---|---|---|
| Messages sent | 11 | 10 |
| Reached n8n | 11 (100%) | **10 (100%)** |
| Turn duration — min | 8.8 s | 8.7 s |
| Turn duration — **median** | 10.5 s | **9.2 s** |
| Turn duration — max | 14.6 s | 14.8 s |
| Failed executions | 0 | **0** |
| Failed nodes | 0 | **0** |

**Peak concurrency: 13 executions running simultaneously** at 17:38:21.

Turns were, if anything, marginally *faster* under 13× concurrent load than when run
one at a time. There is no queueing collapse and no error at this level.

30 executions in total: 10 real turns, 10 Room Availability sub-workflow calls, and
10 loop-filtered runs from Jessie's own replies.

## The critical check: guards still ran

`Guard Probe` **ran 10 times out of 10, zero failures, max 79 ms.**

This is the check that matters most, because a failing Code node **fails open** — the
reply still reaches Slack, just with none of the safety checks applied, and nothing
looks wrong from outside. Under this load every guard ran on every turn.

Every other node also ran 10/10 with zero failures.

## One node did degrade

| Node | Serial | Under burst |
|---|---|---|
| **Get Booker** | 1,107–1,511 ms | **3,364 ms** |
| Gate Context | 3,711 ms | 3,580 ms |
| Jessie AI Agent | 5,152 ms | 3,591 ms |

`Get Booker` roughly tripled. It has been recorded before as spiking to 8.5 s with no
known cause — **concurrency now looks like the explanation.** Worth noting for capacity
planning, but it did not fail and did not break the turn.

## Cost of the burst

Measured from the executions, not estimated: **~18,000 prompt tokens per model call,
two calls per turn**, so roughly 37,000 input tokens and under 200 output tokens per
turn. Ten turns ≈ **370,000 input tokens**, which at Flash-Lite-class rates is about
**four US cents**.

Storage: roughly **5 MB** written to the n8n database for the burst (~420 KB per turn).

For scale, since it matters for the 25 September launch: the full reference data —
room table, session types, room ranking — is injected into the prompt on *every*
message. That is why each turn costs ~37k tokens regardless of how short the question
is. At 500 turns a day that is 9–18M tokens daily. Cheap, but it is the dominant cost
driver and it scales directly with message volume.
