## What the failures have in common

1. **Carry-over between requests (6: A2, A4, B4, D1, D2, F2).** What a request "is about" is assembled from the thread:
   Booked For's requester text, Gate Context's carried date, the early room check's carried room, the model's own reading of
   the transcript. The boundary between one request and the next is fuzzy, so a declined or finished request bleeds into the
   next one - a project and time onto a vague request, an old session type into a new one (and then a question that cannot be
   answered), an old time window onto an availability question. **This is the long-thread problem, and it is structural:
   every fix so far drew the boundary for one case.**
2. **Free-text extraction gaps (4: A1, A3, A5, C1).** Taglish dates, typos, "for 2 hours", two bookings in one message. Each
   can be patched, but the space of phrasings is open-ended.
3. **Model wording around code (2: A6, B2) and one order slip (B1).** The code question (v258) takes over only when the model's
   reply ends in a question; statement-shaped asks get through.

What held: everything that is a code decision once the details are right - cards, the confirmation gate, taken-room handling,
cancel and move by a loose reference, refusing to double-book, internal rooms, series.

## Reading it for the pivot

- A **form per booking** removes classes 1 and 2 for bookings: each submission is one request with its own fields (date
  picker, time pickers or start + length, studio select, session type select, project, client), so nothing carries over and
  nothing is parsed from free text. Code writes every prompt and error (class 3).
- **Availability questions** (D1, D2, F2) carry over too. Either they get the same treatment (a small "check availability" form
  or buttons), or questions stop inheriting booking context unless they name it.
- **Cancel and move** did well in chat (E1, E2) - buttons on a list of the requester's bookings would make them deterministic
  as well and cover PENDING 100.
