# Outage record — Slack event delivery, 2–3 September 2026

Written 2026-09-04 from n8n's API, the Docker logs for both days, and the Slack
message history for `D0BTP8VQ6UB`. Every timestamp below is **Asia/Manila**.

> The Docker log files are named `...-PHT.log` but the timestamps **inside them are
> UTC**. Add 8 hours. Two earlier readings of these logs went wrong on this alone.

## Summary

Two unrelated faults, wrongly treated as one recurring outage.

| | 2 September | 3 September |
|---|---|---|
| Scope | Jessie only — Posty ran throughout | Jessie; Posty also silent, but may simply have had no traffic |
| Shape | Per-message loss, interleaved with successes | Continuous, 16:59:46 → 18:21:09 |
| Cause | Signing-secret mismatch (well supported); **what introduced it is not yet pinned**. Plus a separate, proven webhook deregistration 17:25–17:43 | **Open** |
| Fixed by | Credential update at 17:43:23 | Nothing identifiable; recovered on its own |

**SQLite was not the cause of either.** See *What was ruled out*.

The premise that both outages "started late afternoon" was an artifact. 15:03:35 on
2 Sept was **Posty's** last execution, not a Jessie event. It was never a Jessie
timestamp, and the "recurring afternoon window" was built on it.

## 2 September — resolved

### Root cause

n8n's Slack Trigger validates every request against the **signing secret held in the
node's credential**. Jessie's trigger was moved off the credential she shared with
Posty (`nmFoMiSOz2wjLG1I`, now named `Posty Slack (Bot)`) onto a newly created
`Jessie Slack (signed)` (`EcX8szEJrOLYLUfl`) whose secret did not match the app
actually sending her events.

Every genuine Slack event was rejected with 401. **No execution row, no log line at
`info` level, and the endpoint answers a probe identically to a healthy one.** That
is why four separate investigations found "n8n healthy, webhook registered".

A second, independent fault overlapped it from 17:25 to 17:43: the production webhook
was **deregistered** while someone attempted test-listens. n8n logged this plainly.

### What is proven vs inferred

**Proven** — all from n8n's own API and logs: the credential's create and update
timestamps; that v113's trigger used Posty's credential and v116's used the new one;
that the production path was logged unregistered at 17:27/17:30/17:36/17:43,
interleaved with test-listen refusals; that delivery went clean 20 seconds after the
credential update.

**Inferred** — that the credential's secret was wrong. The fix is solid: credential
updated 17:43:23, clean 1-second delivery 4.5 minutes later.

**NOT established — whether publishing v116 caused it.** The publish sits seven
minutes before the first proven drop, which is suggestive, but nobody tested Jessie
between 1 Sept 18:23:42 and 2 Sept 16:14:57. She could have been broken for up to
22 hours beforehand, and the publish may simply be when someone next looked. Two
possibilities remain live:

  a. The 1 Sept 14:12:21 version still used `nmFoMiSOz2wjLG1I`, and publishing v116
     moved her onto the bad credential — the publish is the cause.
  b. The 1 Sept 14:12:21 version already used `Jessie Slack (signed)` (created
     31 Aug 21:42, seventeen hours earlier). She then worked correctly under it all
     of 1 Sept evening, so its secret was right at that point — meaning something
     rotated it Slack-side afterwards and v116 is coincidental.

There is no file for the 1 Sept publish (the v114/v115 numbering skip), so the repo
cannot separate them. **Reading that version's Slack Trigger credential in Workflow
History settles it in one look.**

**An anomaly neither variant explains.** Exec 4381 got through at 17:10:15 —
mid-outage, 61 seconds after the message, the shape of a Slack retry landing. A
statically wrong secret rejects every attempt, retries included. So either the fault
was intermittent rather than constant, or something changed around 17:09 that appears
in neither the credential's `updatedAt` (17:43:23 only) nor any log line.

### What it is not

Not the credential — `Jessie Slack (signed)` shows `updatedAt` 2 Sept 17:43:23 and
nothing since. Not a restart — there is no SIGTERM anywhere in the 3 Sept log. Not
test-listen — no "limitations in Slack Trigger" line that day. Not SQLite, load, or
lost execution rows, per the table above.

### Leading suspect: Slack-side delivery throttle or disable

Jessie's app spent nearly all of 2 September returning failures to Slack — 401s from
the signature mismatch, then 404s from the deregistered webhook. Posty's endpoint
returned 404s too (16:26:18). That is the condition Slack counts toward throttling or
disabling an app's event delivery. A full day of failures on the 2nd followed by an
unexplained 81-minute cutoff on the 3rd is a plausible cause and effect.

**This is checkable and nobody has looked:** each app's Event Subscriptions page shows
delivery failure counts and any disable event, and Slack emails the app owner when it
disables one.

### Second suspect: Cloudflare dropping Slack's POSTs

Something in front of n8n already blocks by user-agent — the 3 Sept log has
`Blocked GET /assets/... for "Slackbot-LinkExpanding"` at 17:47:31 and a
Facebot/Twitterbot block at 20:00:04. A rule that blocks Slack's link crawler is a
rule that could match Slack's event POSTs. Check Cloudflare → Security Events,
filtered to the webhook path, across both windows.

Note that probes from Howard's machine reached n8n and were logged *during both
stalls*, so Cloudflare→n8n was up. Any surviving explanation has to be either
Slack not sending, or Cloudflare dropping Slack's requests specifically.

## Also found — not outage causes

**JS task-runner starvation, and worsening.** `No matching task offer for request
(type "javascript"). Available offer types: [python]` went 2 → 12 in a day; JS runner
re-registrations went 46 → 102. A JS Code node that cannot get a runner is a task that
cannot run. Likely behind the "tiny hiccup" replies at 12:57–12:58 on 3 Sept and the

the VM's networking was unwell that afternoon.

## Corrections to earlier conclusions

- **"401 to an unsigned probe means healthy and registered."** It does not. 401 is also
  exactly what a genuine Slack event gets when the signing secret is wrong. The probe
  cannot distinguish a healthy endpoint from one rejecting every real event. This single
  ambiguity is why the cause went unfound for two days.
- **The production webhook path is `/webhook/<id>/webhook`.** `/webhook/<id>` returns
  404 and is not the endpoint. Some early "not registered" log lines were probes on the
  wrong path — but the ones at 17:27–17:43 on 2 Sept used the **correct** path and were
  genuinely unregistered. That distinction was missed, and it was the whole answer for
  that window.
- **Jessie and Posty were not always separate apps.** v113 shows Jessie's trigger using
  `nmFoMiSOz2wjLG1I` — the credential now named `Posty Slack (Bot)`. They shared one
  app until 31 Aug, and the split is what broke Jessie.
- **"Both outages started late afternoon."** Artifact. There are 32 gaps of 15+ minutes
  across the three days, spread through every hour. Gaps are quiet periods, not drops.
  Only a Slack message with no matching execution is evidence of a drop.
- **The 3 Sept prune did not fix anything.** 2 Sept recovered after a restart; 3 Sept
  recovered with neither restart nor prune. Pruning remains worth keeping on its own
  merits — ~2 MB Posty payloads with no retention policy is not sustainable — but it is
  not the fix for this.

## For CLAUDE.md

Gotchas this incident earned, none currently documented:

13. **Never test-listen or unpublish a live Slack Trigger workflow.** n8n cannot listen
    for test and production events at once, and its own advice — "Unpublish the workflow
    to execute" — silently tears down the production webhook. Slack's POSTs then 404 and
    vanish. Proven cause of the 2 Sept 17:25–17:43 loss.
14. **A wrong signing secret is invisible.** Wrong credential → 401 on every event, no
    execution, no log line at `info`, and probes look identical to healthy. Test with a
    *signed* request: `./scripts/webhook-canary`.
15. **The production webhook path is `/webhook/<webhookId>/webhook`.** 401 = registered.
    404 = not registered. `/webhook/<webhookId>` is always 404 and proves nothing.
16. **Docker log timestamps are UTC** even when the filename says PHT.
17. **A silent auth failure is invisible until someone tests.** Jessie only runs when
    someone talks to her, so a broken publish looks exactly like a quiet afternoon.
    Run `./scripts/webhook-canary` after every publish, and on a schedule.

## The Cloudflare tunnel connector is largely cleared

- It runs as a **Kubernetes pod** (`cloudflared-859f98bbfb-vzm9q`), one continuous pod
  Aug 11 → Sept 8 with **zero restarts**. So the "connector machine sleeps overnight"
  hypothesis is **dead** — it's an always-on pod, not a Mac.
- During the two clean outages (**3 Sept morning, 5 Sept 13-hour**), the connector logged
  nothing but a daily cosmetic version-nag — no reconnects, no "lost connection to edge",
  no origin errors. If the tunnel had been dropping, there would be reconnection storms.
  There were none.
- The origin-unreachable errors it *did* log (`connection refused` to `192.168.0.230:5678`)
  all coincide with **n8n container restarts** (2 Sept troubleshooting, 7–8 Sept
  hardening) — maintenance noise, not the outage.
- **Caveat:** cloudflared only logs an origin error when the edge hands it a request.
  "Silent during 5 Sept" is consistent with both "healthy" and "edge stopped routing to
  it." Only the **Cloudflare dashboard** distinguishes these — see
  [CLOUDFLARE-CHECK.md](CLOUDFLARE-CHECK.md).
- **Action regardless:** cloudflared is on `2025.2.1` (flagged outdated, ~18 months old).
  Upgrade it — rolling restart of the k8s deployment, low risk.

## Correction (9 Sept): the DHCP lease loss was admin-triggered, not the mechanism

An earlier version of this section claimed the DHCP lease loss was "the outage mechanism
captured at small scale." **That was wrong.** The two lease-loss events (≈06:46 and 06:50
UTC on 8 Sept) were **caused by an administrator running `sudo netplan apply`** — the
system journal shows `n8nadmin ... COMMAND=/usr/sbin/netplan apply` at 06:46:19 UTC, with
the lease loss following 2 seconds later. So they show what a deliberate 4-second network
blip looks like; they **do not** show DHCP caused the Sept 3/5 outages, and a 4-second
reacquire cannot be extrapolated to a multi-hour outage.

A **DHCP reservation for `192.168.0.230` is still worth doing — as preventive hardening,
not a confirmed root-cause fix.** (Credit: Genzo's technical review caught this.)

## Correction (9 Sept): overnight was not "clean" — a real message dropped

An earlier version claimed "no outage overnight." **Also wrong.** The VM/endpoint were
healthy (canary green every ~65 s all night), but **a real Slack message still dropped**:

- Tara messaged Jessie "Test" at **2:12 AM**; Jessie did not reply.
- The debug log (which records every webhook n8n receives) shows only the 65-second canary
  probes around 18:12 UTC — **no receipt for her message, and no execution.**
- Real Slack events reaching Jessie were **absent 00:32 → 09:04 AM PHT (8.5 h)**; her
  12:06 PM re-test got through normally.
- At 2:12 AM the VM was healthy (canary green, no network event) → **the message was lost
  upstream of the box**, between Slack and the tunnel.

**The key lesson:** reachability checks (the canary, `/healthz`, an external uptime
monitor) test whether the endpoint *answers* — not whether Slack's events *arrive*. A
message can drop while every check stays green. This is why earlier investigations kept
finding "n8n healthy, webhook registered" during the outages: the endpoint was always
reachable; the events just weren't arriving. My earlier "2am ata = just a guess" reading
was wrong — Tara's screenshot shows a genuine failed interaction.
