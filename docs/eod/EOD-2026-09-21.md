## Relative date resolution ("next Thursday") — verified correct, rule kept, test-locked

A QA had reported "next Thursday" landing a week too far — booking from **Fri 3 Sep 2027**, "next
Thursday" came back as **16 Sep** instead of the expected **9 Sep** ("next-next Thursday"). Ran it
down.

**Finding: the live build is already correct; no code change to the resolver.** Relative dates are
resolved **deterministically in `Gate Context`** (not by the model), then injected into the prompt as
"already resolved, use exactly," with `Guard Probe` fixing any wrong weekday printed beside a date.
Reading the live code, simulating the exact formula, and `test-gate` all agree: from Fri 3 Sep, "next
Thursday" = **9 Sep**. It does not produce 16 Sep from a Friday. The QA's 16 Sep was the **old,
pre-deterministic build** (the model used to resolve dates and flip-flopped — Sep 9 one run, Sep 2
minutes later on the identical prompt, which is why it was moved into the node), or a **Mon–Wed
reference** (see below). The incident execution itself has aged out — n8n keeps only ~a day.

**The rule (Tara's, 2026-08-30; re-confirmed 2026-09-21 — keep):** weeks start Monday.
- "this Thursday" = Thursday of the current week
- "next Thursday" = Thursday of the **next** calendar week
- bare "Thursday" = the nearest upcoming Thursday

"next X" and "nearest upcoming X" **differ only when today is Mon–Wed** (this week's X still ahead) —
then "next X" is a week further out. From Fri–Sun they coincide. So **16 Sep is correct from a
Mon/Tue**, and 9 Sep is correct from Fri 3 Sep. Someone who means the sooner one on a Mon–Wed says
the bare weekday ("book Thursday") or an explicit date. Jessie always shows the resolved date **and
weekday** in the summary before the (yes/no), so a misread is catchable at confirmation.

**Recorded + locked:**
- `docs/design/date-resolution.md` — the design, the rule, the Mon–Wed nuance, and the safety net,
  so the next QA doesn't re-flag it (commit `c0a5b6e`).
- `test-gate` — new scenario "next on a Monday is the following week": today = Mon 6 Sep 2027 →
  "next Thursday" = 16 Sep, locking that the resolver doesn't collapse to nearest-upcoming. Added a
  per-case "today" override to the harness. Now **28 gate scenarios**; full suite still **145 checks**
  (commit `06eb13c`).

No workflow deployed today — the resolver was already correct; this was verification, documentation,
and a regression lock.
