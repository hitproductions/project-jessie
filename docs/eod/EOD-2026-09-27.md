## System prompt: size and where it goes

Measured on live main (v160):

- The rendered prompt is **~32k characters**, about 8k tokens by n8n's estimate. That estimate leaves out
  the 13 tool schemas, so the real total is ~12–15k tokens.
- Tara's "40k/44k" figures were **characters, not tokens**. Her v157 trim took it from 47,084 to 29,223
  characters.
- Only **~2k characters are data** (room table, session types, room names). The other ~30k are rules
  for every flow, sent on every message whatever the request is.
- Largest sections: Rooms 4.6k, Rules for every request 2.9k, Reference 2.7k, What you need 2k, Who is
  who 2k, Look up before booking 1.8k, Recurring 1.6k, preemption 1.5k.

Conclusion: trimming more text is not the lever. Every rule that has held is one that moved into code
(the one principle in `CLAUDE.md`), and the eval below points at the same thing.

## The eval: what was built

- **`scripts/eval-twin`** generates a test copy of live main, **"ZZ Jessie Eval Twin (test copy - do not
  use)"**, id `KRZmVfKIwCiLREjz`.
  - Only the 11 Slack- and consent-facing nodes are swapped, under the same names, plus one webhook input.
  - A guard refuses the copy if any other node differs from live. It's 42 of 53 nodes byte-identical:
    same prompt, same Gemini model, same Gate Context, Guard Probe and Booked For, and the same live
    sub-workflows, Airtable and calendar.
  - It's rebuilt from live on every run, has a random webhook path, and is **inactive except while a run
    is in progress**. Confirmed inactive tonight.
- **`scripts/eval-run`** does the whole run, then switches the copy off:
  - rebuild, upload, re-guard, activate
  - send each scenario 5 times
  - score each reply against the tool outputs and Airtable reference data, not fixed expected text
- **Safety:** the script refuses to send any "yes", so the confirmation gate can never pass, and it
  aborts if any write tool reports success. None did. Nothing was posted to Slack.
- **`docs/eval/scenarios.json`**: 49 scenarios. 28 core (engineers, clients, dates, booked-for,
  durations, what's free, missing details), plus 21 automatable rows from `Jessie_QA_Sheet 0830`.
- Raw results stay local in `eval/results/` (git-ignored: they hold real names and schedule data). Only
  the write-up is committed.

## Results in one screen

- **Held:** engineers 67 of 67 (none invented; an unknown name refused 5 of 5), dates 30 of 30,
  booked-for detection 15 of 15, past dates refused, lookups and "not found" correct, no false "Booked"
  claims.
- **1. Padded timestamps read as "every room free" (bug in our code).**
  - When the model glues junk onto a time (`+08:00hq`, `…p`, `…Cllr`, U+FE0F, Khmer letters), Room
    Availability sends the raw text to Google. Google rejects it, the node carries on after the error,
    and "no events" becomes "all free". The `isoOnly()` cleanup from gotcha 16 runs *after* the query.
  - **79 of 199 checks in the eval (40%), and 4 of 27 on live since 24 Sep.** In 7 of 10 requests Jessie
    offered Studio F on 7 Oct 2027, which is booked.
  - Book Session's own conflict query has the same gap: a padded time makes it fall back to searching
    *now + 24 h*, so its check looks at the wrong day. Its create step then gets the raw time. Whether
    that fails or books over a session is **unverified** (it needs a controlled write). Live: 0 of 14
    booking, move and series calls since 24 Sep were padded.
  - Move Booking's new-window check follows the same pattern.
  - **Fix:** clean before the query, and fail closed on a calendar error.
- **2. Summary drift:**
  - five date formats
  - "Project" vs "Project Title"
  - the calendar title shown in only 23 of 97 summaries
  - one summary printed twice with a garbled line

  This is the case for **Prepare Booking**: code renders the summary.
- **3. The prompt's example leaks.** "Studio 8, Dhang's usual room, is free" was copied into real
  replies: "Dhang" appeared 3 times, and Jem Lim's usual room was given as Studio 8 10 times (it's Studio
  F). Root cause: the Clients tool returns `Preferred Room Names` as a **record id** (`rec36To…`), not a
  name, so the model guesses. The "data unlock is done" note in `CLAUDE.md` *Not done* is not accurate.
- **4. Small leaks:**
  - the tool's "List exactly these and no others." pasted into 2 replies
  - "last-resort" with a hyphen gets past Guard Probe
  - "Sasa Abella (Producer)", with the Airtable role glued onto the name
- **Speed:** median 9.9 s per turn, p90 11.8 s, on the test copy. Live whole-turn median is 11.8 s,
  including Slack. None of the proposed fixes adds a model call.
