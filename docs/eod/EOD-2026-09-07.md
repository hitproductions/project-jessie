### Concurrency / flood test (Genzo's request)

Ten identical read-only availability questions fired **overlapping** — all ten hit
Slack in a 13.4-second window (17:38:08–17:38:21), so with ~9 s turns the early ones
were still running when the last arrived. **Peak 13 executions running simultaneously.**

- **No degradation.** 10/10 reached n8n, 0 failed executions, 0 failed nodes. Median
  turn 9.2 s under load vs 10.5 s serial — if anything faster. No queueing collapse.
- **Every guard ran under load.** `Guard Probe` executed 10/10, zero failures, max
  79 ms. This was the risk worth checking: a failing Code node *fails open* (reply still
  goes out, unprocessed), so green here means no turn slipped through unguarded.
- **`Get Booker` degraded** — tripled from ~1.2 s to 3.36 s under load. Likely the cause
  of its previously-unexplained 8.5 s spikes: concurrency.
- **The flood is what exposed the A1 non-determinism.** Ten identical asks gave two
  answers — 7× the complete 21-room list, 3× a truncated 15-room list. A single serial
  ask would have looked like a systematic bug; it took the repeats to see it is a coin
  flip with the correct answer as the majority outcome.
- **Cost, measured not estimated:** ~18k prompt tokens per model call, ~2 calls/turn.
  The whole 10-message burst ≈ 370k input tokens ≈ **~4 US cents**, and ~5 MB of DB
  growth. Note for launch: the full reference data is injected into the prompt on *every*
  message, so each turn costs ~37k tokens regardless of question length — the dominant
  cost driver, scaling linearly with volume.

### Outage investigation — where it landed

Two investigation threads ran in parallel and reached different conclusions. **Tara's
`OUTAGES.md` is the stronger one and supersedes the Slack/credential framing** below —
it carries evidence the execution-data thread did not have. Reconciled position:

- **It is a recurring network-path failure, not Slack and not n8n.** The GitHub backup
  runs from *outside* the network and hits n8n's API directly (not Slack); at ~05:00 on
  4 and 5 Sept it could not reach the box at all. Both bots drop and recover at the
  **same second** (5 Sept: Posty 13:03:13, Jessie 13:03:31). n8n's own scheduled jobs
  ran *during* the outages, so n8n was alive. Conclusion: alive inside, unreachable from
  outside → the fault is the path between the box and the internet. Leading suspect is
  the **Cloudflare tunnel (`cloudflared`) dropping and reconnecting**; the decisive check
  is its log from a failure window. `EAI_AGAIN` DNS errors appear minutes before each
  failure and are likely a trigger.
- **Correcting the "two proven faults on 2 Sept" claim** (Tara's question): only one was
  proven, and it was self-inflicted. The **webhook deregistration 17:25–17:43** is real
  in the docker log — but it came from someone *test-listening on the live Slack Trigger
  while troubleshooting*, so it was us poking it, not the outage. The **signing-secret /
  401 mismatch was inferred, not proven** — from a credential update at 17:43:23 landing
  ~4 min before recovery — and is now most likely **coincidental**: a message got through
  mid-outage at 17:10 (a Slack retry, which a static wrong secret cannot explain), and
  5 Sept recovered with no credential change at all.
- **Two "fixes" that were coincidences.** The 2 Sept credential update and Tara's 3 Sept
  manual prune each looked like the fix because recovery followed — but **5 Sept
  recovered with neither**. Both were coincidental with a network recovery.
- **SQLite / pruning ruled out as a cause** — no SQLite/lock/disk errors in the logs,
  contiguous execution IDs, no latency creep before any stall, the heaviest hour ran
  fine, and 5 Sept recovered with no pruning. Pruning is still worth keeping on its own
  merits; it was never the fix.
- **Date caveat (Tara's flag): the execution-based timeline is blind to pruned windows.**
  Tara manually pruned on 3 Sept, and both 2 and 3 Sept execution data is now fully gone
  (oldest live execution is 4 Sept). The two docs also describe *different* windows on
  3 Sept — `OUTAGES.md` the morning (~09:00–10:20), the execution thread the afternoon
  (16:59–18:21) — likely two separate events that day. **Dates worth double-checking
  before this goes further.**
- **5 Sept (00:05–13:03, ~13 h) is the best-documented outage and is absent from the
  execution-data doc** — its window was pruned before that analysis ran. `OUTAGES.md` is
  the authority for it.

## DNS / network context for Genzo

The outage is a **network-path problem** (see above), so this is the primary server-side
work, not a side note. Per `OUTAGES.md`, in likely order:

1. **`cloudflared` tunnel log from a failure window** — the one check that decides it. If
   the tunnel disconnects and reconnects at the outage times, it is the tunnel; if the
   log is clean but the box was unreachable, it is the link/ISP itself.
2. **`EAI_AGAIN` / DNS** — appears minutes before each failure (16:02–17:03 on 2 Sept;
   also before the 4/5 Sept windows). Likely a trigger for the tunnel drop. Check the
   box's resolver; try a fixed one (1.1.1.1 / 8.8.8.8).
3. **Site internet / dynamic IP / DHCP lease change** — could break tunnel routing
   overnight, which matches the timing.
4. **External uptime monitor on the public URL** (UptimeRobot / Better Stack /
   Cloudflare Health Checks) — watches from outside, so it catches the drop even when the
   box's own network is down. Highest-value thing not yet in place; needs accounts, not
   code. Note this is *external* to the on-box canary, which cannot report its own host
   being unreachable.
