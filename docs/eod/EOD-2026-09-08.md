## 2. Outage investigation — reconciled with Tara

Tara's [OUTAGES.md](../../OUTAGES.md) is now the authoritative account and **supersedes
the earlier Slack/credential framing**:

- **It is a network-path failure, not Slack and not n8n.** The GitHub backup runs from
  *outside*, hits n8n's API directly (not Slack), and still failed to reach the box on 4
  and 5 Sept. Both bots drop and recover the same second (5 Sept: Posty 13:03:13, Jessie
  13:03:31). n8n's own scheduled jobs ran *during* outages. Alive inside, unreachable
  from outside → the fault is between the box and the internet. Leading suspect: the
  **Cloudflare tunnel (`cloudflared`) dropping**; `EAI_AGAIN` DNS errors appear minutes
  before each failure.
- **Corrected an overclaim** (Tara's question): of the "two proven faults" on 2 Sept,
  only the webhook deregistration (17:25–17:43) was real — and it was **self-inflicted**
  by test-listening on the live Slack Trigger *while troubleshooting*, not the outage.
  The signing-secret mismatch was **inferred, not proven**, and is most likely
  coincidental (a message got through mid-outage at 17:10, which a static wrong secret
  can't explain; 5 Sept recovered with no credential change).
- **Two "fixes" that were coincidences:** the 2 Sept credential update and Tara's 3 Sept
  manual prune each preceded a recovery — but 5 Sept recovered with neither.
- **Date caveat:** the 3 Sept manual prune makes any execution-gap timeline unreliable;
  2–3 Sept execution data is fully pruned now. Dates worth double-checking.
- **To do:** reconcile the two outage docs into one on the network-path conclusion.

### The tunnel gap + working hypothesis

The connector **does not run on this VM**, so none of the five VM logs can see it drop.
The new instrumentation still helps: next outage, the VM logs will show the box healthy
and DNS resolving — *isolating the fault upstream by elimination.*

**Hypothesis — the connector machine sleeps.** An hours-long outage that recovers around
midday is not normal `cloudflared` behavior (it reconnects in seconds); it fits the
connector's *host* going away overnight. If that host is a Mac, tunnel-drop (#1) and "Mac
power management" (#4) are the **same root cause**. **Top question for Genzo: what machine
runs `cloudflared`, and does it sleep?**
