## 1. Recurring bookings — Stage 2 (server-side loop), live and verified

Recurring bookings are now **fully deterministic end to end**. The model passes only the
pattern; n8n computes the dates and creates the series. Builds on Stage 1 (18 Sep, `Expand
Series`).

- **NEW `Jessie — Book Series`** (`UAwFoifgkfL1xNP2`): on "yes" the agent calls it once with the
  pattern + booking details. It expands the dates, loops **Book Session** per date via an
  Execute-Sub-workflow node (`mode:each`), skips any date whose room is taken, and returns a
  booked/skipped summary. The model no longer drives the loop or the dates.
- **main v127–v128:** Book Series tool wired to the agent; Guard Probe's claim check accepts
  `book series`/`BOOKED_SERIES`; the prompt's "on yes" step calls Book Series once instead of
  looping Book Session. v128 fixes a missing `Booked by | ref:` on series events (see below).
- **`verify-ids`** now tracks Expand Series + Book Series (id + active state), after Expand
  Series silently defaulted inactive when created via the API (CLAUDE.md gotcha 0).

### Notifications to the booker — built and deployed (cancel + move)

When an authorized coordinator moves or cancels a booking that isn't theirs, Jessie now DMs the
**booker** to tell them. Built into both sub-workflows (cancel-booking-v7, move-booking-v6, main
v136): `Check Ownership` / `Resolve Booking` compute `notify` (true only when a coordinator acts on
someone else's booking — never on the owner's own change), the booker's id (`ref:`), and the message;
a `Notify?` IF gates a best-effort `Notify Booker` Slack DM (a send failure can't undo the
cancel/move). A `requester_name` input carries the actor's name into the message.

reroutes every notification to Howard while we build, with the body prefixed
`[DEV] would notify <name> (<id>):` so we see exactly what each real person *would* have received —
no real users are pinged. Set the constant to `''` at launch and the same code DMs the real people.

## 4. Booking event log → Google Sheet — LIVE

Every calendar mutation now appends a row to a Google Sheet (`Jessie Booking Log`, tab `Log`), via a
service account (`jessie-booking-log@…gserviceaccount.com`) with the Sheet shared to it — no human
Google account, isolated from the shared OAuth credential. Columns: Timestamp · Action · Title ·
Room(s) · Date · Time · Department · Booker · Done by · Event ID · Note.

- **book-session-v32 / cancel-booking-v10 / move-booking-v9:** a `Build Log Row` Code node + a
  best-effort `Log to Sheet` node (`serviceAccount` auth, `onError` continue) at each mutation point.
  Book logs only on `Verify` status `CREATED` and re-emits Verify via a `Return Booked` passthrough
  so the tool result is unchanged; Cancel/Move log just before their notify chain. **Book Series
  inherits** `BOOKED` per occurrence (it books each via Book Session). `Done by` records the actor,
  so a coordinator's action on someone else's booking is visible.
- Validated the Sheets node on a throwaway webhook first (config: typeVersion 4.5, `gid=0`,
  auto-map), then **live end to end**: a booking wrote a `BOOKED` row, a cancel wrote `CANCELLED` —
  both nodes `success`, returns unchanged. Row logic unit-tested in `workflows/drafts/logging/`
  (14 checks). `Log to Sheet` runs ~2.5 s (a real API call) so `health` flags it >1 s — expected,
  best-effort, can't block a booking.
