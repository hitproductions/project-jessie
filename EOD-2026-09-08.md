Five VM-side log sources, so the **next** outage is captured instead of reconstructed:

   (workflow activation, webhook handling, Slack/API errors, SQLite errors, runner activity)

   (RAM, disk, CPU/load, DNS, public health, Docker container states, Postgres readiness,
   SQLite size, time sync)
4. **Docker logs** — containers: `n8n`, `n8n-runners`, `postgres-pgvector`, `redis`,
   `bookstack-stack-bookstack-1`, `bookstack-stack-bookstack_db-1`

   daemon, systemd failures)

## The one open gap: the Cloudflare tunnel

**Everything except the top suspect is now either fixed or instrumented — and the top
suspect is the only thing still invisible.** The tunnel connector runs on another
machine, so none of the five VM logs will ever show it dropping. Image/report from
Genzo says this outright: those logs must come from that machine or from Cloudflare.

The new instrumentation still helps, even blind to the tunnel: next outage, the VM health
log + canary will show DNS resolving, the box healthy, the webhook route present locally
— i.e. *"everything here is fine."* That **isolates the fault upstream by elimination** —
provably not the VM, pointing at the tunnel or the connector machine. "We don't know"
becomes "it's not the box."

### Hypothesis worth testing: the connector machine sleeps

The suspect table lists #4 as "Mac power management (sleep overnight)," which never fit an
Ubuntu VM on TrueNAS. But if the machine running `cloudflared` **is a Mac**, then #1 and
#4 are the **same root cause**: a Mac running the connector sleeping overnight drops the
tunnel and matches everything — both bots down the same second, self-recovery on wake,
box healthy throughout, nothing in n8n's logs, overnight-to-midday timing.

**Top question for Genzo: what machine runs `cloudflared`, and does it sleep?**
