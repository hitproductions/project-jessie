# Handoff — 3 September 2026

Three things changed today: a scheduled cleanup workflow that keeps the instance
alive, and two fixes to `Guard Probe`, the node that rewrites Jessie's reply on
the way out to Slack.

Read this alongside `ONBOARDING.md`, which covers how the system is put together.
Everything below has been checked against the live build. Where something is
unproven, it says so.

---

## 1. Jessie — Prune Executions

**Why it exists.** Jessie and Posty both stopped answering on 2 September and
again on 3 September. Deleting 3,781 stored executions brought them back both
times. Every message Jessie handles stores a full execution record — roughly
250 KB per turn, about 15 MB per four hours of use — and it all lands in a
single-file SQLite database that n8n also uses to serve the editor. Nothing was
ever cleaning it up.

**What it does.** A new workflow, `Jessie — Prune Executions`, runs once a day
and deletes stored executions older than three days. It is active now. Five
nodes and a note on the canvas: a schedule trigger, a paginated list call, a
filter that decides what is past the cutoff, the delete call, and a summary.

Two settings live at the top of the `Older Than Cutoff` node:

- `KEEP_DAYS = 3` — how much history to keep
- `MAX_PER_RUN = 800` — a ceiling per run, so one pass can never sit there for
  an hour

**The trap, if you ever rebuild this.** The first version looked like it worked
and deleted nothing. The executions API returns records **newest first** and
caps the page size at 250, so fetching one page and filtering by age finds
nothing old and reports success. It needs cursor pagination to reach the old
records at all. Related: the pagination parameter n8n accepts carries only
`name` and `value` — adding a `type` field fails validation with a confusing
message about `body, headers, qs`.

**What is still unresolved.** Nobody has captured the container logs from a
failure window, so *why* a large execution table takes the instance down is
still a hypothesis rather than a finding. Two further things need shell access
on the server and are worth doing:

- Deleting rows does not shrink the database file. That needs a `VACUUM`.
- The real fix is moving off SQLite to Postgres. Pruning buys time; it is not a
  solution.

**One caveat.** The schedule says 04:00, but no timezone is set on the workflow,
so it fires in whatever the server's default timezone is. That has not been
verified. Jessie herself is unaffected — she resolves Manila time in code.

## 2. Guard Probe — two bugs, both fixed

`Guard Probe` is the last node before Slack. Anything that must be true of the
*text* is enforced there, because every one of these started as an instruction
in the prompt and every one of them failed as an instruction.

### The weekday beside a date was wrong on most dates

Jessie writes dates like "Friday, September 10, 2027". Two corrections run over
that: one for dates that carry a year, one for dates that do not. The second one
had a subtle fault in its pattern — it would accept the first digit of a
two-digit day and ignore the rest, so it computed the weekday for the **1st of
the month** and rewrote the line to match.

The effect: any date with a two-digit day came out with the wrong weekday. The
launch date, 25 September 2026, printed as a Thursday. It is a Friday.

It hid for two reasons. It quietly undid the *correct* correction that runs
before it, so that one looked like it was doing nothing at all. And booking
summaries use a different format — `September 10, 2027 (Fri)` — which this
pattern never matched, so only prose sentences were affected. That is why it
survived fifteen builds.

### Someone else's booking was relabeled as yours

Every summary carries a `*Booked by:*` line. Because the model sometimes
mistypes a name it copies, that line was being rewritten from Airtable — on the
assumption that the person booking is always the person asking.

That assumption is wrong for a cancellation or a lookup, which show you someone
*else's* booking. Asked to cancel a booking held by another engineer, Jessie
correctly found the real owner and then printed the requester's name instead —
directly contradicting the refusal in the next sentence, in the one situation
where the name is the entire point.

It now only overwrites a name when both of these hold: the name appears nowhere
in what the tools actually returned that turn, **and** it is a near-miss of the
real one. A mistyping is neither reported by a tool nor a plausible different
person; another person's name is reported by a tool, and is nobody's typo.

## 4. How to check any of this yourself

Type these in a terminal, from inside the project folder.

Everything the checks know about, run against the workflows n8n currently has
stored:

```bash
./scripts/test-nodes --live
```

That is 108 checks plus 27 scenarios for the confirmation gate. If a document
and a check disagree, believe the check.

What the live workflow actually *did* on its last few turns — per-node status
and timing:

```bash
./scripts/health
```

**Run that one after every import.** The two commands answer different
questions, and the difference has mattered: a build once left `Guard Probe`
failing on every single message while every stored-definition check passed. A
failing node still lets the reply reach Slack, just with none of its corrections
applied, so nothing looks wrong from the outside.

## 5. Still open

- **A seeded test event needs deleting.** `GUARDCHK / Bea Jose / HL`, Studio 6,
  Friday 10 September 2027, 10:00–11:00. It was created to test the refusal to
  cancel another person's booking, and it carries a fake booker reference. It is
  on a 2027 date so it cannot collide with anything real.
- **Engineer initials in booking titles are composed by the model** with no
  lookup behind them. A wrong set of initials becomes a wrong calendar title.
  Fixing it properly means adding an engineer lookup inside `Book Session`,
  which is a design decision, not a repair.
- **Recurring bookings are not supported.** Each session has to be requested
  separately.
- **The QA year shift must be switched off before launch.** `YEAR_SHIFT` at the
  top of `Gate Context` and the matching one-year offset in the system prompt
  are what put test bookings in 2027. They have to go to zero **together** —
  change one and the model and the guards will disagree about what day it is,
  which decides what "next Thursday" means and whether a date is in the past.
